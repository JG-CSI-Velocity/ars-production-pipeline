# Equation Dictionary — Velocity Pipeline

**What this is.** A per-analysis catalogue of every analytics module in the pipeline: the input DataFrame(s) it consumes, the metrics/equations it computes (grounded in real source columns), the denominator each rate anchors to, and whether the output lands on a slide.

Generated by reading `01_Analysis/00-Scripts/analytics/**` against `docs/MODULES.md`, `SLIDE_MAPPING.md`, `docs/SLIDE_SPECS_ARS.md`, `docs/slide_specs/*.yml`, and the `01_Analysis/00-Scripts/output/` deck machinery. Every equation is quoted from source — nothing here is inferred formula.

> Snapshot at commit `b2d0180` (main after PR #242). Regenerate when analytics change.

## How to read this

- **Cell / module** — the `.py` file (structured `AnalysisModule` packages list their class; legacy notebook sections list numbered cells).
- **On a slide?** — determined by the capture mechanic, not by guesswork:
  - **TXN notebook sections:** a cell renders a chart with `plt.show()` → captured to a `TXN-<SECTION>-NN` screenshot slide; a cell that only `display()`s a table or is pure data-prep → **no slide**.
  - **ARS structured modules:** a module's `AnalysisResult` is placed by its `docs/slide_specs/<section>.yml` spec onto the declared ARS slide IDs (e.g. `A08.x`); scalars it exports flow through `ctx.results` into headlines/callouts.
- **Denominator** — every rate is anchored to the pipeline's 4-layer denominator framework (see below). Where a section's *stamped* label disagrees with what the code actually divides by, it is flagged here and collected in the Appendix.

## The 4-layer denominator framework (the "LAW")

Every rate in the pipeline must anchor to exactly one of these — no bespoke per-chart denominators:

| Layer | Meaning |
|---|---|
| **Eligible** | Accounts meeting the section's eligibility rule (the primary base for most rates) |
| **Eligible Personal** | Eligible ∩ personal accounts |
| **Eligible Business** | Eligible ∩ business accounts |
| **Open** | All open accounts (broadest; descriptive only) |

TXN sections apply the Eligible filter centrally via `txn_wrapper._inject_eligible_filter`. A rate that divides by "all accounts" is on the **Open** layer regardless of what its spec label says.

## dctr — ARS
**Input DataFrame(s):** `ctx.subsets.eligible_data`, `open_accounts`, `eligible_personal`, `eligible_business`, `eligible_with_debit`; `ctx.data` (Total stage of funnels only); `branch_mapping` from `ctx.settings`/config. L12M cuts use `filter_l12m(df, ctx.start_date, ctx.end_date)` on `Date Opened`.
**Denominator:** **Eligible** is the default/law-anchored base for every rate (`dctr()` divides by `len(df)` of an Eligible-derived slice). Exceptions: **DCTR-2 = Open** (whitelisted methodology slide, stamped `denominator_label="Open"`); P/B cuts anchor to **Eligible Personal** / **Eligible Business** (both subsets of Eligible). The two funnels' "through rate" is anchored to **Total** while their "DCTR among eligible" is **Eligible**. Only DCTR-1/2/3 stamp `denominator_label`/`denominator_n`; the A7.x charts do not.
**Deck section / slide IDs:** Debit Card Take Rate — `DCTR-1`…`DCTR-16` + `A7.2`…`A7.15`. Main-deck picks (`Y`): DCTR-3, DCTR-9, DCTR-10, DCTR-11, A7.4, A7.6a, A7.7, A7.8, A7.10a; rest are `A` (appendix/aux deck). Composed main slides: `DCTR-MAIN-1 = [A7.6a, DCTR-7]`, `DCTR-MAIN-2 = [DCTR-2]`, `DCTR-MAIN-3 = [DCTR-4, DCTR-5]`.

**Core formula (everywhere):** `dctr(df) = with_debit / total` where `total = len(df)` and `with_debit = debit_mask(df, debit_col).sum()` (`debit_mask` = universal has-debit predicate over `Debit?`/detected col ∈ {Yes,Y,TRUE,1,D,DC,Debit}). `_helpers.py::dctr`.

# Analytics Equations — Sections: rege, rege_overdraft, attrition

Scope notes:
- **rege/** is the audited ARS `AnalysisModule` package (status.py, branches.py, dimensions.py, _helpers.py). Every rate anchors to **Eligible Personal w/Debit** via `reg_e_base()`. Feeds the deck + Value (A11.2) + Insights.
- **rege_overdraft/** is a parallel TXN notebook-cell section (`TXN_SECTIONS["rege_overdraft"]`, code `REGE`, `txn_wrapper.py:361`). Operates on the raw `rewards_df` snapshot (ALL accounts, not the 4-layer eligible base) and adds OD-limit / revenue / migration analyses that rege/ does not compute.
- **attrition/** is the audited ARS `AnalysisModule` package. Rates anchor to the attrition-specific **L12M Exposure** base (`_helpers.l12m_attrition`), on the **full book** (`ctx.data`) by default; `ARS_ATTRITION_ELIGIBLE_ONLY=1` opts into the eligible-comparable book.

"On a slide?" key (from `docs/manifest_defaults/{rege,attrition}.yaml` + `deck_builder` routing):
- **Main** = SLIDE_MANIFEST `Y` and rendered in the main deck.
- **Appendix** = `A` (deck_builder routes to appendix; still a slide).
- **Data-only** = result discarded / no chart; only populates `ctx.results` for a downstream consumer.

### rege vs rege_overdraft overlap

**Computed by BOTH (but on different denominators / column sources):**
- **Reg E opt-in rate** = opted-in ÷ base. rege/ base = **Eligible Personal w/Debit** (`reg_e_base`), status from the single most-recent `Reg E Code {Mon}{yy}` column; rege_overdraft base = **ALL accounts in `rewards_df`**, status keyword-classified from monthly `Reg E Desc`. Same formula shape, materially different numbers.
- **Monthly opt-in trend over time** — rege/ A8.3 (L12M) + A8.12 (24-mo polyfit slope); rege_overdraft `03` (full discovered window, polyfit slope). Both report pp/month.
- **Opt-in by demographic segment** — overlap only on **age** (rege/ A8.5 account age, A8.6 holder age; rege_overdraft `07` age_band).

**Only rege/:**
- Opt-in by **branch** (A8.4a/b/c, A8.13 pivot) — rege_overdraft has no branch cut.
- **Historical by year / decade** (A8.2).
- **Eligibility→Reg E funnels** (A8.10/A8.11, Open→Eligible→w/Debit→Personal w/Debit→Reg E).
- Opt-in by **product code** (A8.7) and **account-age** buckets (A8.5).
- Debit-holder filtering and the audited 4-layer denominator label + `denominator_n` stamping.

**Only rege_overdraft:**
- **OD Limit** amount analytics entirely — distribution/bands (`05`), avg-limit trend (`06`), avg-limit KPI (`02`). rege/ never reads the `OD Limit` columns.
- **Status migration matrix** first→last month (`04`) and per-account `status_changed`/`change_direction` tracking.
- **OD-fee revenue exposure + erosion scenarios** (`08`, `10`) on hardcoded $30×4 assumptions (rege/ leaves dollarization to the separate ARS Value module A11.2, which uses config `ic_rate`/`nsf_od_fee`).
- **Balance-band × opt-in risk matrix** (`09`) and opt-in by **balance band** / **engagement tier** (`07`).
- Narrative **action summary / recommendations** cards (`10`).

**Verdict:** Not true duplicates — they are ARS-vs-TXN variants that share only the core opt-in rate plus a trend and an age cut, computed on **different denominators** (audited Eligible-Personal-w/Debit vs all-TXN-accounts) and **different source columns**; rege_overdraft is a broader OD-limit + revenue + status-migration exploration, while rege/ is the deck-and-Value-feeding, denominator-law-compliant opt-in section.

# G4 — TXN Analytics Equations: `txn_setup` + `general`

Source: `01_Analysis/00-Scripts/analytics/{txn_setup,general}/`. These are notebook-cell scripts executed in order by `analytics/txn_wrapper.py` inside one shared `namespace` (globals like `combined_df`, `rewards_df`, `monthly_summary`, `portfolio_kpis` persist cell-to-cell and across sections).

## How these cells become slides (mechanism, applies to both sections)

`txn_wrapper.py::ChartCapture` monkeypatches `plt.show()` / `savefig` and saves **every matplotlib figure** a cell renders to a PNG. Each captured PNG becomes an `AnalysisResult(slide_type="screenshot", layout_index=8)` with a runtime slide id **`TXN-GEN-NN`** (section code `GEN`, `NN` = 1-based capture order), per `TXN_SECTIONS["general"] = {"code": "GEN"}`. Consequences:

- A cell that calls `plt.show()` → **produces a screenshot slide** (subject to `SLIDE_MANIFEST.xlsx` `Keep?` = Y/A/N on the `GEN` prefix).
- A cell that only calls `display(styled)` (pandas Styler HTML) or `print(...)` → **no matplotlib figure → NOT a slide**; it only builds shared DataFrames for downstream cells.
- `general/` declares **no entries in `analytics/txn_exports.py`** (only `competition` 13/24 and `executive` 1/5 do). So `general` writes **nothing to `ctx.results`** and binds to **no YAML slide-spec** (`docs/slide_specs/txn_exec.yml` covers only `executive`). Every `general` slide is a raw screenshot, headline-less at the analytics layer.

## Denominator anchoring (the LAW, `docs/MODULES.md` §1 + §5)

`txn_wrapper.prepare_shared_namespace` runs `_inject_eligible_filter(namespace, ctx)` **after** `txn_setup` builds `combined_df`/`rewards_df`. It intersects `primary_account_num` against `ctx.subsets.eligible_data` (`Acct Number`), replacing `combined_df`/`rewards_df` **in place** with the Eligible slice (originals stashed as `combined_df_all`/`rewards_df_all`). So every `general` rate that divides by a `combined_df`/`rewards_df` total is anchored to **Eligible** — matching `txn_exec.yml` (`TXN KPI rates anchor to the Eligible base`). Caveat: this is enforced by the wrapper *upstream*, not inside the cells; if `eligible_data` is unavailable the filter no-ops (`ELIGIBLE_FILTER_APPLIED=False`) and the same code divides by the raw TXN universe (Open-ish, unenforced). TXN does **not** run the `pipeline/steps/audit.py` rate audit, so these denominators are not machine-verified.

# G5 — TXN Analytics Equations: merchant, mcc_code, transaction_type

**Runtime model (all three sections).** These are notebook-cell scripts executed in numeric order by
`analytics/txn_wrapper.py::_execute_scripts` inside one shared namespace built by `analytics/txn_setup/`
(10 scripts). The setup layer concatenates raw TXN files into `combined_df` (transaction-level rows:
`transaction_date, primary_account_num, transaction_type ∈ {PIN,SIG,ACH,CHK}, amount, mcc_code,
merchant_name, merchant_consolidated, terminal_location_1/2, terminal_id, merchant_id, institution,
card_present, transaction_code, source_file` + merged `business_flag` from the ODD + derived

`txn_setup/06-merchant-name-consolidation.py`. `business_df`/`personal_df` are `combined_df` split on

`SECTION_EXPORTS` in `txn_exports.py`, so **none write scalars into `ctx.results`** for the slide-spec
renderer — every slide is a captured screenshot, headline-templated only if a `docs/slide_specs/*.yml`
entry exists (none ships for MERCH/MCC/TT).

# G8 — TXN Analytics Equations: business_accts, personal_accts, product, balance, relationship

## Cross-cutting mechanics (applies to all five sections)

These are **TXN notebook-cell sections** wrapped by `analytics/txn_wrapper.py::TXNSectionWrapper`.
Numbered scripts (`01_*.py` … `NN_*.py`) run in order sharing **one namespace** built once by
`prepare_shared_namespace()`. That setup:

- Loads TXN files → `combined_df` (transaction-level) and the ODD → `rewards_df` (account-level).
- `txn_setup/09-oddd-account-type.py` merges `Business?` from `rewards_df` onto `combined_df` as
  `business_flag` (normalized to `Yes`/`No`), then splits: `business_df = combined_df[business_flag=='Yes']`,
  `personal_df = combined_df[business_flag=='No']`. Also stamps `transaction_date`, `year_month`,
  and dataset-range constants `DATASET_START/END/MONTHS/LABEL`.
- **`_inject_eligible_filter()` filters BOTH `combined_df` and `rewards_df` to the ARS-side eligible book**
  (`ctx.subsets.eligible_data` account IDs) *before* any section runs — enforcing the 4-denominator
  framework on TXN. So every base below is already ∩ **Eligible**. (`combined_df_all` / `rewards_df_all`
  keep the pre-filter escape hatch.) If eligible config is missing it no-ops and falls back to the
  unfiltered universe (logged WARN).

**"On a slide?" rule:** `ChartCapture` intercepts `plt.show()` and saves every open matplotlib figure as a
PNG. Each captured chart becomes one `AnalysisResult(slide_id=f"TXN-{code}-{i+1:02d}", layout_index=8,
slide_type="screenshot")`. So a cell that calls **`plt.show()` → lands on a slide**; a cell that only calls
**`display(styled)` (HTML table) → NO figure → NO slide** (it prints/returns HTML, never captured). Slide
numbering `i+1` is the **sequential chart-capture index**, not the file number — table-only cells consume no
number. Section codes: `business_accts→BUS`, `personal_accts→PERS`, `product→PROD`, `balance→BAL`,
`relationship→REL`. Manifest default (`output/manifest.py`) is **blank = keep**, so emitted slides ship
unless the operator marks `N` in `SLIDE_MANIFEST.xlsx` (BUS→"TXN - Business", PERS→"TXN - Personal" have
rows; PROD/BAL/REL keyed by code).

**Denominator caveat:** almost none of these are denominator-framework *rate-of-X* metrics. They are
within-segment **transaction shares** (`txn_pct = txn_count / total_segment_txns`), **account-level
descriptive stats** (median balance, product counts), or **concentration** figures. The *population base* is
anchored to a framework layer per section per the table headers below, but the individual ratios divide by a
segment-local total, not by the canonical Eligible-rate base. None of these sections stamp `denominator_label`
(they are not `AnalysisModule` rate emitters). Column names are the real TXN/ODD columns.

# G6 — competition + financial_services (TXN analytics equations)

Source root: `01_Analysis/00-Scripts/analytics/`. Both sections are notebook-cell
style (numbered `.py` run in-order by `txn_wrapper.py` in a shared `exec()`
namespace), **not** the `AnalysisModule` ABC. Every chart a cell renders becomes
a deck slide `TXN-{code}-{NN}` where `NN` is **chart order, not script number**
(`txn_wrapper.py:479`). Section codes: competition = **COMP**, financial_services
= **FIN** (`txn_wrapper.py:350-351`).

**Denominator reality (read before the tables):** the competition slide spec
(`docs/slide_specs/competition.yml`) stamps `denominator_label: Eligible`, but the
actual TXN code divides account-penetration rates by
`combined_df['primary_account_num'].nunique()` — i.e. **all accounts present in the
transaction data**, which maps to the **Open** layer of the 4-layer LAW, not ARS
`Eligible`. There is no eligible-status/product filter anywhere in either section.
So every "% of accounts" metric below is anchored to **Open (all card accounts in
the TXN file)**; the `Eligible` label on the two spec'd slides is aspirational, not
computed. Wallet-share % metrics are anchored to **per-account total card spend**
(a within-account share, not a portfolio denominator).

### competition/68 vs financial_services/20 detection overlap

**Verdict: parallel-but-distinct. They share the diagnostic *design/reporting
shape* and the untagged-discovery idea, but run on two completely separate tagging
engines with different data structures, keyword sets, and category taxonomies. No
matching code is shared or imported between them.** (fin/20 header even says
"Mirrors the design of competition/68".)

**Shared (structural / conceptual):**
- Same 4-part report skeleton: (1) per-category txn+account+pattern counts incl.
  empties, (2) top-5 tagged merchants per category (sanity check), (3) **unmatched
  merchants containing financial keywords** = the "discovery list" to grow config,
  (4) a spend/opportunity roll-up.
- Same discovery mechanic: take rows not tagged, `str.contains` a hard-coded
  financial-keyword regex, group by merchant, rank by txns/spend, print candidates
  to paste back into the config cell.
- Both key their per-category loop off the config's own category dict
  (`ALL_CATEGORIES` vs `FINANCIAL_SERVICES_PATTERNS.keys()`) so empties surface.

**Distinct (the actual matching logic — no overlap):**
- **Different tagging engines.** competition tags via
  `01_competitor_config.tag_competitors` → `_compute_category_codes`
  (`normalize_for_match` with `_CARD_PREFIX_RE` + `_BANK_ABBREV_RULES` collapsing
  FEDERAL CREDIT UNION→FED CU etc., int8 pd.Categorical codes, first-match-wins,
  `_COMP_FP_HINTS` guard). financial_services tags inline in `02_identify` via
  `_fs_normalize` (its own `_FS_CARD_PREFIX_RE` incl. `INTUIT*`, punctuation→space)
  + word-boundary `str.contains` batched at 80, minus `false_positive_patterns`.
  The two normalizers are separate code with different rules (68 has bank-abbrev
  canonicalization; 20 does not).
- **Different consumed state.** 68 reads `competitor_txns`, `combined_df`,
  `COMPETITOR_MERCHANTS`, `ALL_CATEGORIES` (and audits `CLIENT_CONFIGS` membership —
  the "#1 cause of empty CU/local-bank buckets", a check with no analog in 20).
  20 reads `financial_services_data` (a category→{transactions,merchant_summary}
  dict) + `combined_df` + `FINANCIAL_SERVICES_PATTERNS`.
- **Different keyword sets & taxonomies.** 68 keyword regex is bank/CU-centric
  (`BANK|CREDIT UNION|CU|FEDERAL CREDIT|SAVINGS|MORTGAGE|FINANCIAL|LENDING`) plus a
  dedicated **BNPL audit**; 20 uses a broader 30+ `_FIN_KEYWORDS` list
  (INSURANCE/INVEST/BROKER/CRYPTO/ADVISOR/WEALTH/RETIREMENT/401K/IRA/HSA/FSA…) and
  a "unmatched spend by keyword" ranking with no BNPL audit.
- **Different taxonomies being audited:** competition = institutions
  (banks/CUs/ecosystems); financial_services = products/services (loans, insurance,
  crypto, tax) — by explicit design ("Other Banks removed… competitor bank
  detection is handled by section 06").
- **Different single source of truth shared *upstream*, not in the diagnostics:**
  both BNPL/wallet/P2P pattern lists derive from `UNIVERSAL_ECOSYSTEMS` (finserv
  cell 01 imports them from competition's config), so the *ecosystem patterns*
  overlap by construction — but that is config sharing, not diagnostic-logic
  sharing.

Bottom line for de-dup: you could extract a common `render_detection_diagnostic()`
skeleton (the 4-section report + discovery-list helper), but the tagging/normalizer
internals are genuinely different and must stay per-section.

### ICS_cohort vs ics_acquisition overlap

**Verdict: same product ("did the instant-issue / ICS acquisition channel produce better card behavior?")
but disjoint data planes, disjoint cohort definitions, and essentially no shared code — they overlap in
*theme*, not in *computation*.**

- **Data plane is the fork.** `ICS_cohort` reads the **account-level ODD** (`data = odd_df = ctx.data`) and
  never opens `combined_df`. `ics_acquisition` reads **transaction-level `combined_df`** joined to
  `rewards_df`. Same underlying client, two different grains (one row per account vs one row per swipe).
- **"ICS" is defined differently.** `ICS_cohort` requires `ICS Account=='Yes'` **AND** `Stat Code ∈
  ELIGIBLE_STATUS_CODES` (a status-eligible ∩ ICS holder cohort, often further ∩ `Debit?`).
  `ics_acquisition` keys off **`Source` (REF/DM)** as the channel identity and treats `ICS Account` Yes as
  merely the gate; it never applies a Stat-Code / eligibility filter and splits the population by
  acquisition channel, not by activation state.
- **Different comparators.** `ICS_cohort`'s spine is **ICS vs Non-ICS** (retention/survival/TTFS/activation
  lift). `ics_acquisition`'s spine is **REF vs DM vs Non-ICS** (channel economics). Neither computes the
  other's headline: only `ICS_cohort` does Kaplan-Meier survival, log-rank, TTFS, cohort-milestone
  activation; only `ics_acquisition` does per-swipe avg-ticket, merchant preference, spend-bracket, and
  monthly transaction-share.
- **Nearest-neighbor metrics that *look* alike but aren't reconcilable:**
  - "Activity/retention": `ICS_cohort` cell 25/29/41 `% Active = (L12M swipes>0)/cohort` (account+monthly-column
    based) vs `ics_acquisition` cell 08 `activity_rate = active-this-month accts / channel accts`
    (transaction-presence based). Different numerators, different denominators.
  - "Spend": `ICS_cohort` uses ODD monthly `%b%y Spend` columns (`Total L12M Spend`); `ics_acquisition`
    uses transaction `amount`. Not the same figure.
  - "Branch": `ICS_cohort` cells 09/13/28/38/46 cut ICS accounts by branch; `ics_acquisition` has no branch
    cut (that lives in the separate `branch_txn` section).
- **Denominator posture is shared only in the negative:** both sit **outside** the 4-layer Eligible LAW —
  `ICS_cohort` on a bespoke ICS/status cohort base, `ics_acquisition` on the raw transacting universe.
- **Zero shared runtime state.** `ICS_cohort` builds `ics_cohort*`, `cohort_milestones_activation`,
  `ics_cohort_personas`; `ics_acquisition` builds `ics_agg`, `ics_merged`, `ics_df/ics_ref_df/ics_dm_df`.
  The only common injected globals are theme (`GEN_COLORS`) and the (undefined-in-prod) `display_formatted`
  shim. The order gap (170 vs 175) and separate codes (ICSA vs ICSC) mean they emit two independent slide
  runs into the same ICS deck.

**Net:** treat them as **two lenses on ICS, not duplicates.** `ics_acquisition` = channel-economics view
on transactions (REF vs DM); `ICS_cohort` = lifecycle/survival view on accounts (ICS vs Non-ICS). Merging
them would require reconciling grain (txn vs account) and the ICS definition (Source-channel vs
Stat-eligible∩flag) — they are complementary, and the only real redundancy is that both re-derive an "ICS
account" label from the same rewards/ODD fields on their own side of the fence.

# G10 — TXN analytics equations: interchange, payroll, branch_txn, attrition_txn, executive

## How these sections reach a slide (shared mechanics)

These are **notebook-cell scripts** run by `analytics/txn_wrapper.py`, not `AnalysisModule` subclasses. Two independent paths put their output into the deck:

1. **Chart capture → screenshot slide.** `ChartCapture` (in `txn_wrapper.py`) monkey-patches `plt.show()`/`savefig`. **Every cell that calls `plt.show()` produces one PNG**, which becomes an `AnalysisResult(slide_id=f"TXN-{section_code}-{i:02d}", layout_index=8, slide_type="screenshot")`. `NN` is the *chart-capture order within the section*, not the cell number. These are candidate slides; `SLIDE_MANIFEST.xlsx` `Keep?` decisions (matched on the `section_code` prefix) drop/keep them. Cells that only `display()` a styled pandas table or `print()` produce **no** matplotlib figure → **not** captured → not a slide.
   - Section codes (`TXN_SECTIONS` in `txn_wrapper.py`): interchange=`IC`, payroll=`PAY`, branch_txn=`BR`, attrition_txn=`ATR`, executive=`EXEC`.
2. **Scalar KPI export → slide-spec text.** `expose_to_ctx_results()` copies variables named in `analytics/txn_exports.py` (`SECTION_EXPORTS`) into `ctx.results[f"{section}_{n}"]["insights"]`, which YAML slide specs (`docs/slide_specs/txn_exec.yml`) bind into headlines/callouts. **In these 5 sections, the ONLY declared exports are `executive_1` and `executive_5`.** interchange / payroll / branch_txn / attrition_txn export **nothing** to `ctx.results` — their only deck presence is the captured chart PNG.

**Denominator (all 5 sections): Eligible.** `prepare_shared_namespace()` calls `_inject_eligible_filter()`, which replaces `combined_df` and `rewards_df` with rows whose `primary_account_num` ∈ `ctx.subsets.eligible_data` account set (the 4-layer-LAW Eligible base; `combined_df_all`/`rewards_df_all` keep the unfiltered escape hatch). So every frame these sections build (`interchange_df`, `payroll_df`, `br_agg`, `attrition_df`) is already scoped to **Eligible**, and `txn_exec.yml` stamps `denominator_label: Eligible`. Cells that further restrict to "active" (spend>0) or "at-risk" are *numerator framing*, not a denominator-layer change. If eligible config is missing, `_inject_eligible_filter` no-ops with a warning and the base silently degrades to the full TXN universe (Open-ish).

Shared constants come from `txn_setup` via the shared namespace: `PIN_RATE`/`SIG_RATE` (interchange cell 01), `MONTH_LABELS`, `DATASET_MONTHS`/`DATASET_LABEL`, `GEN_COLORS`, `AGE_PALETTE`, `ACCT_AGE_ORDER`, `gen_fmt_*`.

**Input DataFrame(s):** `combined_df` (transactions: `merchant_consolidated`, `amount`, `transaction_date`, `primary_account_num`) → `payroll_df` (one row per eligible account) merged with `rewards_df` demographics (`Account Holder Age`→member_age, `Account Age`→account_age_days, `Avg Bal`/`Curr Bal`, `Prod Code/Desc`, `Business?`, `Branch`).

**Payroll detection (cell 01):** `payroll_detected = keyword_payroll | pattern_payroll`.
- keyword: `merchant_consolidated` matches regex of `PAYROLL|DIRECT DEP…|SALARY|WAGES…` **or** processors `ADP|PAYCHEX|GUSTO|…` **AND** `amount > 0` (credit).
- pattern: account with ≥3 non-keyword credits; bucket by `round(log1p(amount)×20)`; day-gap `diff()` within (acct,bucket); "regular" = gap ∈ [10,18] (biweekly) or [25,35] (monthly); needs ≥2 regular gaps.
- frequency from median gap: ≤9 weekly, 10-18 biweekly, 19-35 monthly, else irregular.

**PFI composite score (cell 08) — 0-20 scale, the precise model:**

| Component | Points | Rule |
|---|---|---|
| `pfi_payroll` | 0 or 5 | `has_payroll × 5` |
| `pfi_balance` | 0-4 | balance (`avg_balance`|`curr_balance`): ≤0→0, ≤1000→1, ≤5000→2, ≤25000→3, >25000→4 |
| `pfi_activity` | 0-4 | quintile of `monthly_txn_rate = total_txn_count / n_months` (pct-rank bins .20/.40/.60/.80) |
| `pfi_products` | 1-3 | `min(n_products, 3)` (distinct `Prod Code` per acct from rewards_df) |
| `pfi_tenure` | 1-3 | `account_age_days`: <365→1, 365-1095→2, ≥1095→3 |
| `pfi_billpay` | 0-1 | 1 if ≥2 merchants each receive ≥3 debits (`amount<0`), else 0 |
| **`pfi_score`** | **0-20** | **sum of the six** |
| `pfi_tier` | — | ≥14 Primary, 9-13 Secondary, 5-8 Tertiary, <5 Incidental |

## attrition_txn — TXN (velocity-based risk)
**Input DataFrame(s):** `rewards_df` velocity columns → `attrition_df`: `last 3-mon spend/swipes`, `last 12-mon spend/swipes` (also `MonthlySpend3/12`, `MonthlySwipes3/12` if present), `Stat Code/Desc`, `Avg Bal/Curr Bal`, `Account Holder Age`, `Prod Code/Desc`. Monthly `MmmYY Spend`/`MmmYY Swipes` columns → `monthly_spend_ts`, swipe matrix. Cells 08/12 also read `combined_df.competitor_category`.
**Denominator:** Eligible (`attrition_df` = eligible-filtered `rewards_df`; tier %s divide by `len(attrition_df)`).
**Deck section / slide IDs:** `TXN-ATR-01..NN` screenshots (Attrition (Velocity), order 220). No `ctx.results` export.

**Velocity + risk model (cell 01) — the core equations:**
- `_safe_velocity(recent, annual) = (recent/annual)×4` (annualizes 3-mo vs 12-mo); if `annual==0`: `0.0` when recent==0 else `2.0`.
- `spend_velocity` = `_safe_velocity(last_3mo_spend, last_12mo_spend)`; `swipe_velocity` likewise on swipes. (>1 growing, <1 declining.)
- `risk_tier` (`_classify_risk`): **Closed** if `stat_desc` matches `closed|revoked|cancelled|charged off|frozen|deceased|bankrupt`; else **Dormant** if (no 3-mo spend AND no 3-mo swipes) OR (`sv<0.2 and wv<0.2`); else **Declining** if `sv<0.8 or wv<0.8`; else **Growing** if `sv>1.1 and wv>1.1`; else **Stable**.
- `at_risk = Declining + Dormant`.

**Overlap note with ARS `attrition`:** conceptually parallel (both bucket Growing/Stable/Declining/Dormant/Closed) but a **different model**. ARS `attrition` (per MODULES.md / SLIDE_SPECS_ARS) is closure-based: `Date Closed` parsing ÷ **L12M Exposure** base (LOCKED), full book. This TXN version is a **velocity proxy** (3mo/12mo spend & swipe ratios) with closure inferred from `Stat Desc` keywords — no `Date Closed`, no L12M-exposure denominator, Eligible base. It is not a substitute for the ARS closure rate. The TXN `retention` section (`health_status`) is yet a third parallel classifier.

## Appendix A — Overlap verdicts (are the "duplicate" sections really duplicates?)

Cataloguing was used to test the consolidation hypotheses. **Most suspected duplicates are not duplicates** — they are ARS-vs-TXN variants or complementary lenses. Merging them would destroy real analysis.

| Suspected pair | Verdict | Evidence |
|---|---|---|
| `rege/` vs `rege_overdraft/` | **Not duplicates** — ARS vs TXN | Share only the core opt-in rate + a trend + an age cut, on different columns/denominators. `rege/` is denominator-law-compliant and feeds the deck + Value; `rege_overdraft/` is a broader OD-limit + revenue + status-migration exploration `rege/` never computes. |
| `competition/68_detection_diagnostic` vs `financial_services/20_detection_diagnostic` | **Parallel but distinct** — shared *shape*, not *logic* | Same 4-part diagnostic report shape + untagged-merchant "discovery" mechanic, but two separate tagging engines (`tag_competitors`/`_compute_category_codes` vs inline `_fs_normalize`), different keyword sets, different taxonomies (institutions vs products). |
| `ICS_cohort/` vs `ics_acquisition/` | **Complementary, not duplicate** | Disjoint data planes (account-level ODD vs transaction-level `combined_df`), disjoint "ICS" definitions (Stat-eligible∩flag vs Source-channel REF/DM), no shared runtime state. |
| ARS `mailer` vs TXN `campaign` | **Twins, shared logic** | `campaign`'s DID cohort-lift is the TXN twin of ARS `mailer` A15.4 — a genuine shared-logic extraction candidate. |

**Real, bounded overlap worth extracting (not deleting):**
- The **detection-diagnostic report shape + untagged-merchant discovery** mechanic (shared by competition/68 and financial_services/20) → one reusable diagnostic scaffold, two tagging engines plugged in.
- The **cohort-lift / DID** computation (shared by mailer and campaign) → one shared helper.
- `cross_cohort/` is **absent from `TXN_SECTIONS`** — it renders no deck slides and is a candidate for removal or wiring.
